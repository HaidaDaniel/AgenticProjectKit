# Documentation Maintenance Checks

Run `node scripts/check-docs-consistency.mjs` directly, or use `pnpm quality`. The hosted quality workflow runs `pnpm quality`, so it invokes the same documentation check and test fixtures.

The checker applies deterministic rules to these sources:

- `package.json` supplies `packageVersion`, the package name, repository URL, and local quality command. `docs/releases/index.md` contains exactly one `<!-- APK_VALIDATED_RELEASE: vX.Y.Z -->` sentinel for `validatedReleaseVersion`, the last published release that passed post-tag validation. These versions may differ during pre-tag preparation.
- The pre-tag candidate state is valid when `packageVersion` is numerically greater than `validatedReleaseVersion`, the package-version release note exists with the matching heading, and stable release claims continue to use the validated version. Equality represents a released and promoted state; a package version below the validated release fails.
- The README quickstart install line is derived from the package name, repository URL, and `validatedReleaseVersion`, not the candidate package version. It stays pinned to the last validated tag until post-tag validation has succeeded.
- The release index table, README, changelog, maturity policy, roadmap, progress page, scope, and documentation home are checked against `validatedReleaseVersion`. The release index's current package/candidate statement is checked separately against `packageVersion`. Historical release-note bodies remain exempt; the current candidate note is checked for its heading, a false latest-validated-tag claim, and direct affirmative publication/availability predicates adjacent to its version. Conditions immediately introducing that subject (`once`, `when`, `if`, `after`, `before`, `until`, or `unless`) and negated predicates remain valid. This bounded check does not interpret arbitrary English prose.
- Promotion chronology is PRE-TAG candidate (`packageVersion` ahead) → exact-candidate validation and hosted CI → immutable tag → POST-TAG cold install/downstream validation → separate bookkeeping change on `main` that promotes the sentinel and stable claims. That bookkeeping change does not alter the tagged candidate.
- Inline relative links and heading anchors are checked only in the README, changelog, documentation home, roadmap, progress page, scope, CLI reference, release index, and maturity policy. External URL availability, reference-style links, raw HTML links, and image targets are not checked. A missing `SECURITY.md` target remains optional; when that root file exists, in-scope links to it are checked normally.
- Fenced `--context` examples in the CLI reference must name paths present in the checkout.
- The generated CLI reference block is compared byte-for-byte with the renderer in `src/cli/command-registry.ts`.
- Rows in the roadmap's **Task state rows** table link one task contract each. The checker discovers task IDs and `State` metadata from `.tasks/` (including archived task files) and compares each row without a maintained ID list.
- The sentinel is tracked data, not proof from a remote API. The checker does not query tags or decide whether external publication or post-tag validation occurred; the release workflow must establish those facts before updating the sentinel. Historical versioned release-note bodies and ADR prose are not scanned for current-value drift.

The rules do not infer product truth from prose, check external links over the network, rewrite documentation, or decide whether an unstructured milestone description is semantically accurate. Keep current task lifecycle state in the structured roadmap table and use review for claims that cannot be decided from exact values. Failures name the source file and line with a concrete correction.
